# AI Consultant Agent

The `/consult` endpoint runs a tool-calling agent ("Bé Song Hỷ") that answers
wedding-planning questions using the real Phố Hạnh Phúc catalog instead of the
model's pretrained guesswork.

## Components

| File | Role |
| --- | --- |
| [`app/services/agent_prompt.py`](app/services/agent_prompt.py) | Persona, tone and grounding rules |
| [`app/services/agent_tools.py`](app/services/agent_tools.py) | Catalog tools, JSON schemas, field allowlists, dispatch |
| [`app/services/ai_text.py`](app/services/ai_text.py) | Provider client, history sanitisation, tool loop |
| [`app/routers/vton.py`](app/routers/vton.py) | `/consult` request/response contract |

## Available tools

| Tool | Purpose |
| --- | --- |
| `search_services` | Services by keyword / category / price range |
| `search_vendors` | Vendors by keyword / category / city / min rating |
| `get_vendor_details` | One vendor plus their services |
| `list_service_categories` | Distinct categories, to ground category filters |

## Request

```jsonc
POST /consult
{
  "message": "Mình cần áo dài dưới 5 triệu ở Hà Nội",
  "sessionId": "<server-issued-id>",             // optional after first turn
  "history": [                                    // optional bootstrap fallback
    { "role": "user",      "content": "chào bạn" },
    { "role": "assistant", "content": "Chào bạn!" }
  ]
}
```

Response:

```jsonc
{
  "reply": "…",
  "sessionId": "<server-issued-id>",
  "toolsUsed": ["search_services"],
  "retrievedServices": [
    {
      "id": "…",
      "name": "Gói áo dài cơ bản",
      "category": "Áo Dài",
      "basePrice": 4500000,
      "currency": "VND",
      "thumbnailUrl": "https://…",
      "vendorId": "…"
    }
  ]
}
```

### Prototype session memory

The first request (or a request with an unknown/expired id) receives a fresh
opaque `sessionId`, generated by the server. The caller echoes that id on later
requests. The backend stores the sanitized recent transcript in process memory;
valid server memory takes precedence over client-supplied `history`. `history`
exists only as a bootstrap/backward-compatibility path.

Memory uses inactivity TTL and a maximum session count. Expired sessions are
removed lazily; when the count limit is reached, the least-recently-used
session is evicted. Memory disappears on process restart and is not shared
between multiple workers or instances. Use a shared durable/cache-backed store
before production or horizontal scaling.

`reply` is unchanged from the previous contract; `sessionId` is additive and
required in responses; `toolsUsed` remains additive and safe for existing
clients to ignore.

`retrievedServices` is additive: the deduped catalog rows the tools returned
during this turn, in the order the tools produced them (price-ascending for
`search_services`). The chat UI renders these as product cards in a row above
the composer, each linking to the parent vendor's page — which is why the system
prompt forbids the model from writing image URLs or links into `reply` while
still allowing it to name services and prices. A turn that retrieves nothing
returns an empty list, and the client keeps the previous row on screen rather
than clearing it.

Only a fixed subset of `SERVICE_PUBLIC_FIELDS` is exposed here (see
`_CARD_FIELDS` in `ai_text.py`). That second allowlist is deliberate: widening
the model-facing projection later must not silently start shipping new columns
to the browser. Vendor rows are not included — the row shows services only.

## Configuration

| Variable | Default | Meaning |
| --- | --- | --- |
| `AGENT_TOOLS_ENABLED` | `true` | Kill switch: `false` degrades to prompt-only replies |
| `AGENT_MAX_TOOL_ITERATIONS` | `4` | Max model→tool→model round trips per request |
| `AGENT_TOOL_ROW_LIMIT` | `8` | Rows returned to the model per tool call |
| `AGENT_MAX_HISTORY_MESSAGES` | `12` | Prior turns accepted/stored |
| `SESSION_TTL_SECONDS` | `1800` | Idle lifetime of anonymous in-memory session |
| `SESSION_MAX_COUNT` | `500` | Maximum concurrent in-memory sessions |

Provider settings (`AI_TEXT_PROVIDER`, `OPENAI_API_KEY`, `OPENAI_BASE_URL`,
`AI_TEXT_MODEL`) are unchanged. The model must support OpenAI-style function
calling; with `AI_TEXT_PROVIDER=google` the agent falls back to a single-turn
reply, since the Gemini function-calling wire format has not been ported.

### Gotcha: shell variables override `.env`

pydantic-settings gives OS environment variables **precedence over `.env`**. If
a stale `OPENAI_API_KEY` is exported in the shell that launched VS Code, it
silently shadows the key in [`.env`](../.env) and every request fails with
`401 Invalid token` — while `.env` looks perfectly correct.

Diagnose and clear it:

```powershell
$env:OPENAI_API_KEY                 # if this prints, .env is being ignored
Remove-Item Env:\OPENAI_API_KEY
python -m uvicorn app.main:app --host 127.0.0.1 --port 8080
```

A key inherited from the launching process is not stored in User or Machine
scope, so it disappears on a full VS Code restart but persists in every
terminal until then.

Also confirm only **one** uvicorn owns the port. On Windows several processes
can end up bound to 8080 simultaneously, and requests hit whichever wins the
race — which makes a fixed bug look unfixed:

```powershell
netstat -ano | findstr LISTENING | findstr :8080
```

## Security properties

These are enforced in code, not by asking the model nicely:

- **No general database access.** There is no arbitrary-SQL or arbitrary-table
  tool. Tables without a tool are unreachable.
- **PII is projected out.** `vendors.email`, `vendors.phone`, `vendors.owner_id`
  and `vendors.address` are excluded by an allowlist in `agent_tools.py`. A new
  column is excluded by default until explicitly added.
- **RLS is preserved.** Tools use the caller-scoped client. The service-role
  key is never used on this path, so the agent cannot read more than the caller
  already could.
- **Only `active` rows.** Draft and suspended vendors/services stay invisible.
- **Bounded work.** Iteration and row caps limit cost and blast radius; the
  final iteration withdraws tools to force a text answer.
- **Client cannot inject a system turn.** `history` accepts only `user` and
  `assistant`; `system` and `tool` roles are rejected at the schema and again
  in `sanitize_history`.
- **Session ids are server-generated only.** `sessionId` is minted with
  `secrets.token_urlsafe`. A client-supplied id is only ever *looked up*; an
  unknown or expired id never becomes a key in the store, so a visitor cannot
  create or claim an id of their choosing.
- **Session memory is bounded.** Stored turns are re-validated, clipped, capped
  to `AGENT_MAX_HISTORY_MESSAGES`, expired by `SESSION_TTL_SECONDS`, and limited
  to `SESSION_MAX_COUNT` sessions with LRU eviction.

### Known limitations

Session ids are bearer-style secrets: anyone holding one can continue that
conversation. They are returned in a response body and, in the prototype
frontend, kept in `sessionStorage`, so the usual token-handling caveats apply
(no logging, HTTPS only). Since the consultant path is anonymous and stores
only the visitor's own transcript, the exposure is limited to that transcript.

Memory is process-local: it is lost on restart and not shared across workers,
so a multi-worker deployment will lose continuity whenever a follow-up request
lands on a different worker.

Catalog text (vendor and service `description`) is written by vendors and is
returned to the model as tool output. A vendor could embed instruction-like
text in a description to try to influence recommendations. The blast radius is
limited — the tools expose no writes and no PII — but ranking manipulation is
possible. Treat vendor-supplied copy as untrusted input and consider
moderation on that field if the catalog opens to self-service onboarding.
